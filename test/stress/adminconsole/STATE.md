## Что сохранено

- Исправление снимков `MultiShardServer` через обычный mutex и тесты к нему.
  В PR #3114 исправление отправлено отдельно от тестов; тесты оставлены в этой ветке.
- Четыре ограниченных сценария параллельного обновления состояния и чтения через
  сканеры admin console / gRPC. Используются объекты SPQR с транспортом в памяти.
- Сборка сценариев включается только тегом `adminconsolestress`.
- `run.py` запускает сценарии отдельно и сохраняет логи, команды и `report.json`.

## Окружение и результаты

Все сборки и проверки выполнялись на `158.160.212.50` в `/home/reshke/spqr`.
Go: `/usr/local/go/bin/go`, версия `go1.27.2 linux/amd64`.
Параметры: `GOFLAGS=-mod=mod`, `GOMAXPROCS=4`, `GORACE=halt_on_error=1`.
Каждому сценарию отведено 30 секунд фаззинга, два worker-процесса.

| Сценарий | Проверяемые операции | Результат |
| --- | --- | --- |
| `FuzzAdminBackendConnections` | Состояние backend во время запросов и чтения статистики | Worker завершился с кодом 66 на `seed#0` |
| `FuzzAdminClientQuantiles` | Обновление времени транзакций и чтение квантилей клиентов | Worker завершился с кодом 66 на `seed#1` |
| `FuzzAdminPreparedStatements` | Обновление prepared statements и просмотр списка | Worker завершился с кодом 66 на `seed#1` |
| `FuzzAdminClientRouting` | Изменение маршрутизации, снимки клиентов и отменяемых запросов | PASS: 12 301 выполнение, 55 новых интересных входов |

Код 66 совместим с завершением race detector, но сохранённые логи не содержат
стеков гонок: родительский fuzz-процесс сообщает только
`fuzzing process hung or terminated unexpectedly: exit status 66`.
Три сбоя пока нельзя считать тремя подтверждёнными дефектами SPQR.

Дополнительные проверки:

- Seed-корпус `FuzzAdminClientRouting` с `-race -count=10`: PASS.
- golangci-lint 2.15.0 для `./test/stress/adminconsole/...` с тегом
  `adminconsolestress`: 0 issues.

Артефакты полного запуска на сервере:
`/tmp/spqr-adminconsole-fuzz-x_5x0li8/` — `report.json` и отдельный `.log`
для каждого сценария. Это временная директория; её содержимое не включено в Git.

## Что осталось проверить

- Получить полную диагностику трёх неуспешных сценариев и проверить, что причиной
  являются ошибки рабочего кода, а не допущения тестового окружения.
- Проверить корректность модели владения соединением в каждом сценарии.
- Улучшить сохранение stderr worker-процессов: сейчас runner классифицирует
  завершение с кодом 66 без стека как `failed`.
- При таймауте завершать всю группу процессов runner, включая дочерние workers.
- В расчёте задержки тестового сценария проверить преобразование `b+1`:
  для `byte(255)` сложение переполняется до преобразования в `time.Duration`.
- После подтверждения причин исправлять их отдельными небольшими изменениями
  и проверять отсутствие гонок на соответствующем сценарии.
